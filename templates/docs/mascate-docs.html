📁 Estructura de archivos

El frontend está dividido en archivos separados por responsabilidad: estructura (HTML), estilos (CSS) y comportamiento (JS). Los archivos estáticos los sirve el backend de FastAPI.

proyecto/ ├── static/ │ ├── css/ │ │ ├── tokens.css ← Variables globales: colores, tipografía, radios │ │ ├── auth.css ← Layout y estilos exclusivos de la pantalla de acceso │ │ └── dashboard.css ← Layout y estilos de los dashboards (sidebar, cards, etc.) │ └── js/ │ ├── auth.js ← Lógica de login/registro + llamadas a /auth/* │ └── dashboard.js ← Lógica de dashboards + fetch de datos por rol ├── templates/ │ ├── mascate-auth-final.html ← Página de login y registro │ └── mascate-dashboards-final.html ← Dashboards (4 pantallas en un mismo HTML) └── backend/ ← Código del equipo de backend (no documentado aquí)

Dependencias entre archivos

El orden de carga importa. Cada HTML carga primero los tokens (base) y luego sus estilos específicos:

<link rel="stylesheet" href="/static/css/tokens.css"> ← primero: variables <link rel="stylesheet" href="/static/css/auth.css"> ← segundo: estilos de auth <script src="/static/js/auth.js"></script> ← al final del body <link rel="stylesheet" href="/static/css/tokens.css"> <link rel="stylesheet" href="/static/css/dashboard.css"> <script src="/static/js/dashboard.js"></script>

⚙️ auth.js

Toda la lógica de la pantalla de acceso. Maneja la UI, valida campos y se comunica con la API. Sin dependencias externas.

Constantes y estado global

const API = 'http://127.0.0.1:8080'; ← cambiar a URL de producción cuando esté lista let selectedRole = null; ← rol activo en el formulario de registro

Inicialización (DOMContentLoaded)

Al cargar la página, hace un GET /dispositivos/ para llenar el select de dispositivos en el formulario de prescriptxr. Si el backend no responde, lo maneja silenciosamente con console.log.

Funciones

FunciónParámetrosQué hace
switchTab(tab) 'login' | 'register' Alterna visibilidad de #loginView y #registerView. Limpia el estado de éxito.
selectRole(role) 'dispositivo' | 'prescriptor' | 'beneficiario' Marca la role-card seleccionada, muestra el bloque #fields-{role}, actualiza selectedRole, muestra el botón de submit.
togglePw(id, btn) id del input, botón Alterna type="password" ↔ type="text" y swapea el ícono del ojo en el botón.
showToast(msg, isError) texto, booleano Muestra el toast por 3s. Si isError=true aplica clase .error (color distinto).
doLogin() — Valida email y contraseña. POST /auth/login. En éxito: guarda token/rol/nombre en localStorage, redirige a /dashboard con 800ms de delay.
doRegister() — Lee los campos del rol activo usando el mapa ROL_FIELDS, valida campos requeridos, POST /auth/register. En éxito: muestra #successView.
goToLogin() — Oculta el successView y vuelve al tab de login.

Estructura de datos por rol

ROL_FIELDS mapea claves del payload de la API a IDs de inputs del HTML. ROL_REQUIRED define qué campo es mínimo obligatorio por rol (además de email y contraseña):

const ROL_FIELDS = { dispositivo: { email: 'regDispEmail', password: 'p1', nombre: 'regDispNombre', lugar_actividades: 'regDispLugar', /* ... más campos ... */ }, prescriptor: { email: 'regPrescEmail', password: 'p2', nombre_completo: 'regPrescNombre', _dispositivo_id: 'regPrescDisp' ← prefijo _ = tratamiento especial (parseInt) }, beneficiario: { email: 'regBenefEmail', password: 'p4', nombre_apodo: 'regBenefNombre' } };
⚠️
Las claves de ROL_FIELDS son los nombres exactos de los campos que el backend espera en el body del POST /auth/register. Si el equipo de backend cambia los nombres de los campos, hay que actualizar este objeto.

⚙️ dashboard.js

Lógica de los dashboards. Lee el rol de localStorage, muestra la pantalla correcta y carga los datos desde la API para cada vista.

Inicialización

const token = localStorage.getItem('mascate_token'); const rol = localStorage.getItem('mascate_rol'); const nombre = localStorage.getItem('mascate_nombre'); ← Si no hay token o rol, redirige inmediatamente a /login if (!token || !rol) { window.location.href = '/login'; }

Flujo de carga

Lee localStorage
→
showScreen(rol)
→
load{Rol}()
→
Fetch API + renderiza DOM

Funciones

FunciónQué hace
showScreen(role)Remueve .active de todas las pantallas y lo agrega a #screen-{role}. También actualiza los botones de la demo-bar.
doLogout()Elimina las 3 claves de localStorage y redirige a /login. Se inyecta un botón de logout en cada .sb-user al cargar.
loadDispositivo()Carga estadísticas, beneficiarixs y actividades del dispositivo autenticado. Actualiza header, sidebar y paneles.
loadPrescriptor()Carga lista de asignados con sus estados. Conecta el botón del formulario de seguimiento al endpoint POST /prescriptores/seguimientos.
loadBeneficiario()Carga actividades disponibles y el detalle del primer dispositivo. Renderiza el grid de actividades.
loadAdmin()Carga stats globales, alertas, tabla de dispositivos y conteos por rol para las barras de progreso.
setStatVal(screen, i, val)Helper: actualiza la i-ésima .stat-val dentro de #screen-{screen}.
setInnerHTML(el, html)Helper: escribe innerHTML solo si el elemento existe (evita errores si cambia el HTML).
authHeaders()Devuelve objeto con Authorization: Bearer {token} + Content-Type, para llamadas autenticadas con body.
authGet()Devuelve solo el header de autorización, para llamadas GET autenticadas (sin Content-Type).
⚠️
loadDispositivo() hace un loop sobre todos los dispositivos del usuario y usa el primero que responde exitosamente. Esto es un workaround temporal — una vez el backend implemente un endpoint /dispositivos/mi-dispositivo, debería usarse ese directamente.

🤝 Contrato frontend ↔ API

Lo que el frontend ya tiene implementado y espera del backend. Esto es lo que el equipo de backend necesita garantizar para que nuestro código funcione sin cambios.

⚠️
JWT aún no está implementado en el backend. Mientras tanto, los endpoints que requieren autenticación pueden no validar el token. Cuando se implemente, el frontend ya está listo — el header Authorization: Bearer {token} ya se envía en todas las llamadas protegidas.

Endpoints de autenticación

MétodoRutaDescripciónAuth
POST /auth/login Autentica usuario. El frontend espera recibir: { access_token, rol, nombre } Público
POST /auth/register Crea cuenta. El body varía por rol — ver payloads abajo Público

Payload registro — Prescriptxr

{ "rol": "prescriptor", "email": "...", "password": "...", "nombre_completo": "...", "perfil_disciplina": "Arte y cultura", "telefono": "...", "dispositivo_id": 1 }

🛡️ Roles y permisos

Los roles los define el backend en el login. El frontend los usa solo para mostrar la pantalla correcta — no hace validación de permisos del lado del cliente (eso es responsabilidad del backend).

RolPantallaPuede hacer en el frontend
🏘️ dispositivo screen-dispositivo Ver stats de su dispositivo, lista de sus beneficiarixs, próximas actividades
🎯 prescriptor screen-prescriptor Ver sus asignados con estados, registrar seguimientos
🌱 beneficiario screen-beneficiario Explorar actividades, ver detalle de dispositivos
🔐 admin screen-admin Ver stats globales, alertas, tabla completa de dispositivos y usuarixs. También ve la demo-bar.
ℹ️
El flujo es: backend devuelve rol en el login → frontend lo guarda en localStorage('mascate_rol') → al cargar el dashboard, showScreen(rol) activa la pantalla correspondiente y load{Rol}() trae los datos.

Lenguaje inclusivo
Toda la interfaz usa lenguaje de género neutro con terminación -x (beneficiarix, prescriptxr). Esto es intencional y refleja el enfoque comunitario del proyecto MASCATE.
Sobre el nombre "Dispositivo CBC"
CBC = Club/Base Comunitaria. Puede ser un parque, salón comunal, sede propia u otro espacio. El término refleja la autonomía territorial del proyecto.
